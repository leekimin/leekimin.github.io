## 왜 필요한가

이전 글에서는 비기능 요구사항을 설계 입력으로 바꾸는 방법을 다뤘다. 그런데 실무에서 가장 강하게 작용하는 제약은 요구사항 문서에 잘 드러나지 않는다. 바로 **배포 환경**이다.

클라우드에서 잘 돌던 서비스를 공공기관 폐쇄망에 납품하면 `docker pull`조차 실패한다. 온프레미스 고객사는 서버 한 대를 늘리는 데 품의부터 입고까지 6주가 걸린다. 환경을 늦게 확인하면 설계를 처음부터 다시 해야 한다.

## 핵심 개념: "무엇이 쉽게 바뀌는가"

세 환경을 기술 스택으로 비교하면 차이가 흐려진다. **변경 비용**으로 보면 근본적인 차이가 드러난다.

| 축 | 클라우드 | 온프레미스 | 폐쇄망 |
|---|---|---|---|
| 용량 확보 | 분 단위, API 호출 | 주~월 단위, 구매 절차 | 월 단위, 반입 심사까지 |
| 외부 의존성 | 관리형 서비스 사용 가능 | 직접 운영 | 모든 것을 내부에 둬야 함 |
| 패키지/이미지 | 인터넷에서 바로 받음 | 프록시 경유 | 미러 저장소, 반입 절차 |
| 비용 구조 | 운영비(OPEX), 사용량 과금 | 자본비(CAPEX), 고정 | CAPEX + 반입 인력 |
| 장애 대응 | 원격, 즉시 | 원격(VPN) | 현장 방문, 보안 USB |

여기서 중요한 설계 원칙이 나온다.

- **클라우드**: 용량은 싸고 빠르다. 대신 **비용 통제와 벤더 종속**이 주요 트레이드오프다.
- **온프레미스**: 용량이 고정되어 있다. 처음부터 **피크 기준으로 산정**하고, 수평 확장보다 수직 여유를 남겨야 한다.
- **폐쇄망**: 외부와 연결되지 않는다. **모든 의존성을 명시적으로 목록화**할 수 있어야 하고, 업데이트는 "배포"가 아니라 "반입"이 된다.

## 예시: 의존성을 미리 드러내기

폐쇄망 납품을 염두에 둔다면 빌드 단계에서 외부 의존성 목록을 뽑는 습관이 필요하다. 아래는 Helm 차트가 쓰는 이미지를 추출해 오프라인 번들로 묶는 예시다.

```bash
# 1. 차트가 참조하는 이미지 목록 추출
helm template myapp ./charts/myapp -f values-prod.yaml \
  | grep -oE 'image: *"?[^" ]+' | awk '{print $2}' | tr -d '"' \
  | sort -u > images.txt

# 2. 이미지를 받아 하나의 tar로 저장 (인터넷 구간)
xargs -a images.txt -n1 docker pull
docker save $(cat images.txt) | gzip > myapp-images-$(date +%Y%m%d).tar.gz
sha256sum myapp-images-*.tar.gz > SHA256SUMS

# 3. 폐쇄망 내부 레지스트리로 적재 (반입 후)
docker load < myapp-images-20261016.tar.gz
while read img; do
  docker tag "$img" registry.internal:5000/"${img#*/}"
  docker push registry.internal:5000/"${img#*/}"
done < images.txt
```

같은 차트를 환경별로 배포하려면 레지스트리와 외부 연동 지점을 values로 분리해야 한다.

```yaml
# values-airgap.yaml
global:
  imageRegistry: registry.internal:5000
external:
  smtp: { enabled: false }        # 외부 메일 불가 → 내부 알림으로 대체
  objectStorage:
    type: minio                   # S3 대신 자체 운영
    endpoint: http://minio.internal:9000
telemetry:
  sentry: { enabled: false }      # SaaS 모니터링 차단
```

`images.txt`에 들어가지 않은 이미지가 하나라도 있으면 현장에서 `ImagePullBackOff`가 난다. 이 목록 자체가 아키텍처 산출물이다.

## 실무에서 주의할 점

1. **관리형 서비스는 "기능"이 아니라 "운영 위임"이다.** RDS를 PostgreSQL로 바꾸면 백업, 페일오버, 패치를 모두 직접 해야 한다. 기능은 같아도 운영 아키텍처를 새로 설계하는 것과 같다.
2. **시간 동기화, DNS, 인증서를 가장 먼저 확인하라.** 폐쇄망에는 공인 NTP와 공인 CA가 없다. 내부 CA 체인을 이미지에 넣는 방식을 초기에 정해 두지 않으면 TLS 오류로 며칠을 잃는다.
3. **라이선스 검증과 SaaS 호출을 찾아라.** 일부 상용 소프트웨어는 기동할 때 외부 라이선스 서버를 호출한다. `tcpdump`로 기동 시 나가는 연결을 한 번 확인해 보는 것만으로도 위험을 크게 줄일 수 있다.
4. **추상화는 경계에서만 하라.** 모든 클라우드 서비스를 감싸는 범용 추상 계층은 비싸다. 스토리지, 큐, 시크릿처럼 환경마다 실제로 달라지는 지점에만 인터페이스를 둔다.
5. **업데이트 주기를 설계 입력으로 받아라.** 폐쇄망은 분기에 한 번 반입하는 경우가 흔하다. 하위 호환성과 DB 마이그레이션 전략이 클라우드보다 훨씬 보수적이어야 한다.

다음 단계에서는 이 제약을 바탕으로 애플리케이션 구조를 모놀리스로 할지 분산으로 할지 판단하는 기준을 다룬다.
