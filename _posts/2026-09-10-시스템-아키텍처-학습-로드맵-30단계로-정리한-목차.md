## 왜 이 주제인가

시스템 아키텍처는 기술 선택의 목록이 아니라 제약 아래서 내리는 판단의 연속입니다. 같은 요구사항이라도 클라우드에서는 관리형 서비스로 해결되는 문제가 폐쇄망에서는 직접 구축과 운영 부담으로 돌아옵니다. 코드를 잘 쓰는 것과 서비스 전체가 버티도록 만드는 것은 다른 능력이고, 후자는 애플리케이션 구조뿐 아니라 데이터, 네트워크, 보안, 스토리지, 배포, 운영까지 하나의 그림으로 볼 때 가능해집니다.

이 로드맵의 목표는 "어떤 아키텍처가 정답인가"를 외우는 것이 아닙니다. 주어진 제약을 읽고, 선택지를 나열하고, 무엇을 포기하는 대가로 무엇을 얻는지 설명할 수 있는 상태가 되는 것입니다. 설계를 남에게 납득시키고 몇 년 뒤에도 근거를 되짚을 수 있다면 충분합니다.

## 전체 목차

1. 시스템 아키텍처란 무엇인가: 설계 결정과 트레이드오프의 정의
2. 아키텍처 품질 속성: 가용성, 확장성, 일관성, 운영성의 우선순위 정하기
3. 요구사항에서 제약으로: 비기능 요구사항을 설계 입력으로 변환하기
4. 환경 제약의 이해: 온프레미스, 클라우드, 폐쇄망의 근본적 차이
5. 애플리케이션 구조: 모놀리식, 모듈러 모놀리스, 마이크로서비스의 선택 기준
6. 서비스 경계 설계: 도메인 분할과 통신 비용의 균형
7. 동기와 비동기: API 호출, 메시지 큐, 이벤트 스트림의 사용 지점
8. 데이터 아키텍처 기초: 관계형, 문서형, 키값, 시계열 저장소의 선택
9. 데이터 일관성 설계: 트랜잭션 경계, 분산 트랜잭션, 최종 일관성
10. 캐시 아키텍처: 계층별 캐시 배치와 무효화 전략
11. 스토리지 아키텍처: 블록, 파일, 오브젝트 스토리지와 백업 설계
12. 네트워크 아키텍처: 세그먼트 분리, 라우팅, 로드밸런싱 계층
13. 보안 아키텍처: 인증, 인가, 비밀 관리, 경계 방어의 배치
14. 폐쇄망 아키텍처: 외부 의존성 제거와 내부 미러링 설계
15. 고가용성 설계: 단일 장애점 제거와 이중화 패턴
16. 확장성 설계: 수직 확장, 수평 확장, 샤딩의 적용 순서
17. 아키텍처 문서화: 다이어그램, ADR, 설계 결정 기록 방법
18. 실습: 요구사항에서 아키텍처 초안 도출하기
19. 실습: 데이터 흐름도와 배포 다이어그램 작성하기
20. 실습: 동일 서비스를 클라우드와 폐쇄망 두 버전으로 설계하기
21. 배포 아키텍처: 환경 분리, 아티팩트 관리, 배포 전략
22. 인프라 구성 관리: 코드형 인프라와 형상 관리의 경계
23. 관측 아키텍처: 로그, 메트릭, 트레이스의 수집과 보관 설계
24. 운영 아키텍처: 장애 대응 체계, 온콜, 런북의 설계
25. 용량 계획: 부하 예측, 리소스 산정, 비용 구조 설계
26. 아키텍처 진화: 레거시 전환과 점진적 마이그레이션 전략
27. 트러블슈팅: 성능 병목의 계층별 원인 분리
28. 트러블슈팅: 장애 전파와 연쇄 실패 차단 설계
29. 트러블슈팅: 데이터 정합성 깨짐의 추적과 복구
30. 아키텍처 리뷰: 설계 검증 체크리스트와 의사결정 회고

## 왜 이 순서인가

1~4단계에서 판단의 기준선을 먼저 세웁니다. 품질 속성의 우선순위와 환경 제약을 정하지 않으면 이후의 모든 선택이 취향 싸움이 됩니다. 5~17단계는 애플리케이션에서 시작해 데이터, 스토리지, 네트워크, 보안으로 계층을 넓히고, 가용성과 확장성이라는 횡단 관심사로 마무리합니다.

첫 번째 고비는 8~9단계입니다. 데이터 일관성은 대부분의 설계 실패가 최종적으로 드러나는 지점이고, 여기서 애매하게 넘어가면 27~29단계의 트러블슈팅이 읽히지 않습니다. 두 번째 고비는 20단계로, 같은 서비스를 두 환경으로 설계해 보면 그동안 무의식적으로 전제하던 것들이 드러납니다.

21단계 이후는 설계한 것을 실제로 굴리는 이야기입니다. 운영과 트러블슈팅을 뒤에 둔 이유는, 무엇이 깨지는지를 알아야 앞의 설계 판단이 비로소 몸에 붙기 때문입니다.
