## 왜 필요한가

지난 글에서 하네스를 "모델 호출 바깥에서 에이전트를 굴리는 모든 것"으로 정의했다. 하네스가 실제로 하는 일의 대부분은 **루프 하나를 안전하게 돌리는 것**이다.

LLM 호출은 한 번에 끝나는 함수다. 입력이 들어가면 출력이 나온다. 하지만 "이 장애 원인을 찾아줘" 같은 작업은 한 번에 끝나지 않는다. 로그를 보고, 의심 가는 서비스를 고르고, 메트릭을 조회하고, 다시 판단해야 한다. 상태가 없는 함수 호출을 상태가 있는 작업으로 바꿔 주는 장치가 바로 추론 루프다.

19년 동안 서버를 운영해 보니 이 구조가 낯설지 않았다. 이벤트 루프, 리컨실레이션 루프(Kubernetes 컨트롤러), 재시도 루프와 구조가 거의 같다. 다만 **다음에 무엇을 할지 정하는 쪽이 코드가 아니라 확률적인 모델**이라는 점이 다르다.

## 핵심 개념

루프 한 바퀴는 세 단계로 이루어진다.

| 단계 | 주체 | 하는 일 |
|---|---|---|
| 관찰(Observe) | 하네스 | 대화 이력과 도구 실행 결과를 컨텍스트로 조립 |
| 판단(Reason) | 모델 | 최종 답변을 낼지, 어떤 도구를 어떤 인자로 부를지 결정 |
| 행동(Act) | 하네스 | 도구를 실제로 실행하고 결과를 다시 관찰로 넘김 |

여기서 중요한 점은 **모델은 판단만 한다**는 것이다. 모델은 "`kubectl logs`를 실행하겠다"는 의도를 구조화된 출력으로 낼 뿐이다. 실제 실행, 권한 확인, 타임아웃, 결과 잘라내기는 모두 하네스가 맡는다. ReAct 패턴이 학계에서 정리한 것도 결국 이 분업이다.

루프가 끝나는 조건은 크게 세 가지다.

1. 모델이 도구 호출 없이 최종 답변을 낸다 (정상 종료)
2. 하네스가 정한 한도에 걸린다: 반복 횟수, 토큰, 비용, 시간 (강제 종료)
3. 복구할 수 없는 오류가 난다 (실패 종료)

## 예시: 최소 구현

특정 SDK에 묶이지 않도록 모델 호출 부분은 추상화해 두었다.

```python
import json, subprocess

MAX_TURNS = 10

TOOLS = {
    "run_shell": lambda args: subprocess.run(
        args["cmd"], shell=True, capture_output=True, text=True, timeout=30
    ).stdout[-4000:],  # 출력 상한: 컨텍스트 폭주 방지
}

def agent_loop(task: str, call_model) -> str:
    messages = [{"role": "user", "content": task}]

    for turn in range(MAX_TURNS):
        # 1) 판단: 모델이 다음 행동을 결정
        reply = call_model(messages, tools=list(TOOLS))
        messages.append({"role": "assistant", "content": reply})

        if not reply.get("tool_calls"):
            return reply["text"]  # 정상 종료

        # 2) 행동: 하네스가 실제 실행
        for call in reply["tool_calls"]:
            try:
                result = TOOLS[call["name"]](call["args"])
            except Exception as e:
                result = f"ERROR: {e}"  # 오류도 관찰 대상
            # 3) 관찰: 결과를 다음 턴 컨텍스트로
            messages.append({
                "role": "tool",
                "tool_call_id": call["id"],
                "content": result,
            })

    return "[중단] 최대 반복 횟수 초과"  # 강제 종료
```

실행 흐름을 로그로 남겨 두면 디버깅이 훨씬 쉬워진다.

```bash
# 턴별 메시지를 JSONL로 남겨 두고 도구 호출만 추려 보기
jq -c 'select(.role=="assistant") | .content.tool_calls[]?.name' trace.jsonl | sort | uniq -c
```

## 실무에서 주의할 점

- **종료 조건은 반드시 하네스가 가진다.** 모델이 "끝났다"고 말해 주기를 기다리면 무한 루프가 생긴다. 반복 횟수뿐 아니라 누적 토큰과 소요 시간에도 상한을 걸자.
- **오류를 삼키지 말고 관찰로 돌려준다.** 예외가 나면 루프를 깨기보다 `ERROR:` 메시지를 넘기는 편이 낫다. 그러면 모델이 스스로 인자를 고쳐 다시 시도한다. 단, 같은 오류가 N번 반복되면 끊어야 한다.
- **관찰 결과의 크기를 통제한다.** 로그 수만 줄을 그대로 넣으면 다음 턴의 판단 품질이 떨어지고 비용이 커진다. tail, 요약, 필터링은 하네스가 책임진다.
- **메시지 이력이 곧 상태다.** 루프 중간에 프로세스가 죽으면 `messages`만 있어도 재개할 수 있다. 이력을 영속화해 두면 재현과 감사가 모두 가능해진다.
- **행동 전에 정책 검사를 넣을 자리를 비워 둔다.** 위 코드의 `TOOLS[...]` 호출 직전이 권한 확인, 사람 승인, 드라이런을 끼워 넣을 지점이다. 이 부분은 이후 단계에서 따로 다룬다.

정리하면 에이전트의 "지능"은 모델에서 나오지만, 신뢰성은 이 루프를 감싸는 하네스 코드에서 나온다. 다음 글에서는 루프의 행동 단계를 이루는 도구 정의와 호출 인터페이스를 살펴본다.
