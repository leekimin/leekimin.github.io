## 코드는 빨라졌는데, 왜 제품은 그대로일까

지난 2년 사이 대부분의 팀에 AI 코딩 도구가 들어왔다. 자동완성이 붙었고, 채팅으로 함수를 뽑아내고, 에이전트가 테스트까지 짜준다. 그런데 이상하게도 분기 로드맵은 눈에 띄게 당겨지지 않는다. 이유는 생각보다 단순하다. **빨라진 구간이 '코드 작성' 하나뿐**이기 때문이다.

기능 하나의 리드타임을 뜯어보면 요구사항 정리, 이해관계자 합의, 설계 리뷰, 구현, 코드 리뷰, QA, 배포 승인으로 나뉜다. 구현이 전체의 20~30%를 차지한다면, 그 구간을 두 배 빠르게 만들어도 전체 개선은 15% 남짓이다. 암달의 법칙이 그대로 적용된다. 나머지 70%는 여전히 사람의 회의와 문서와 대기 시간에 묶여 있다.

AI-DLC(AI Development Life Cycle, AWS는 AI-Driven Development Lifecycle이라는 표현을 쓴다)는 바로 이 지점에서 출발한다. **AI를 기존 프로세스의 부품으로 끼워 넣는 대신, AI가 주도한다는 전제로 생애주기 전체를 다시 그리자**는 제안이다.

## 애자일이 깔고 있던 전제가 바뀌었다

스프린트가 2주인 이유는 무엇이었나. 요구사항을 문서로 옮기고, 설계를 합의하고, 구현하고, 검증하는 데 사람 기준으로 그 정도 시간이 필요했기 때문이다. 백로그 그루밍, 스토리 포인트, 번다운 차트는 모두 '사람의 산출 속도는 예측하기 어렵다'는 전제 위에 세워진 장치다.

AI가 초안을 분 단위로 만들어내기 시작하면 이 전제가 흔들린다. 병목은 더 이상 '만드는 시간'이 아니라 **'결정하는 시간'**이다. 무엇을 만들지 합의하고, 나온 결과가 맞는지 판단하는 일에 시간이 쏠린다. AI-DLC는 그래서 프로세스의 무게중심을 산출에서 의도 명확화와 검증 쪽으로 옮긴다.

## AI-DLC의 세 단계

AI-DLC는 생애주기를 세 단계로 압축한다. 각 단계의 공통 규칙은 하나다. **AI가 초안을 내고, 사람이 방향과 승인을 책임진다.**

- **Inception(착수)**: 비즈니스 의도를 입력하면 AI가 요구사항을 구조화하고, 모호한 지점을 되묻고, 사용자 스토리와 작업 단위(Unit of Work)로 쪼갠다. 기존 기획 단계가 며칠에서 몇 시간으로 줄어드는 구간이다.
- **Construction(구축)**: 논리 설계와 도메인 모델을 먼저 세우고 그로부터 코드와 테스트를 생성한다. 코드부터 뽑는 게 아니라 설계 산출물을 중간 계약으로 두는 것이 핵심이다.
- **Operations(운영)**: 인프라 코드, 배포 파이프라인, 관측 설정까지 같은 컨텍스트 위에서 생성한다. 운영 지식이 사람 머릿속이 아니라 저장소에 남는다.

## 알아둘 세 가지 용어

**볼트(Bolt)** — 스프린트를 대체하는 작업 단위다. 2주가 아니라 몇 시간에서 며칠 단위로 의도 → 산출 → 검증 → 통합을 한 바퀴 돈다.

**몹 일래버레이션 / 몹 컨스트럭션(Mob Elaboration / Mob Construction)** — 기획자, 개발자, QA가 각자 AI를 따로 쓰는 대신 한자리에서 같은 AI 세션을 두고 함께 다듬는다. 해석 차이가 코드에 도달하기 전에 잡힌다.

**명확화 질문(Clarifying Questions)** — AI가 빈칸을 추측으로 채우지 않고 질문으로 되돌리게 하는 규칙이다. AI-DLC에서 가장 실무적인 효과를 내는 부분이기도 하다.

## 실제로는 이렇게 생겼다

거창한 플랫폼이 필요하지 않다. 컨텍스트를 저장소에 두는 것부터 시작한다.

```bash
mkdir -p ai-dlc/{inception,construction,operations}

touch ai-dlc/inception/intent.md            # 비즈니스 의도(사람이 작성)
touch ai-dlc/inception/units-of-work.yaml   # AI 초안 + 사람 승인
touch ai-dlc/construction/logical-design.md
touch ai-dlc/operations/runbook.md

git add ai-dlc && git commit -m 'chore: AI-DLC 컨텍스트 저장소 초기화'
```

Inception 산출물은 산문이 아니라 기계가 읽을 수 있는 형태여야 이후 단계에서 검증할 수 있다.

```yaml
# ai-dlc/inception/units-of-work.yaml
intent: 고객이 배송 시작 전 주문을 스스로 취소할 수 있어야 한다

bolt:
  id: BOLT-07
  timebox: 6h                  # 스프린트가 아니라 시간 단위
  mob: [PO, 백엔드 2명, QA]

units:
  - id: UOW-0142
    title: 주문 취소 시 재고 원복
    acceptance:
      - 배송 시작 전 주문은 취소할 수 있다
      - 취소된 주문의 모든 라인 수량이 재고에 원복된다
      - 배송 시작 후 취소 요청은 409를 반환한다
    open_questions:            # AI가 추측 대신 남긴 질문
      - 부분 취소도 이번 볼트 범위인가?
      - 쿠폰 복원은 어느 팀 책임인가?
    status: awaiting_human_decision
```

Construction 단계의 코드에는 **어느 작업 단위에서 나왔는지**를 남긴다. 나중에 왜 이렇게 짰는지 추적할 수 있는 유일한 끈이다.

```java
// UoW: UOW-0142 (주문 취소 시 재고 원복)
// Source: ai-dlc/inception/units-of-work.yaml
public class OrderCancellationService {

    private final OrderRepository orders;
    private final InventoryPort inventory;

    public void cancel(OrderId orderId, CancelReason reason) {
        Order order = orders.findById(orderId)
            .orElseThrow(() -> new OrderNotFoundException(orderId));

        order.cancel(reason);               // 도메인 규칙: 배송 시작 후 취소 불가
        inventory.restock(order.lines());   // UOW-0142 수용 기준 2번
        orders.save(order);
    }
}
```

마지막으로 볼트의 종료 조건을 CI가 강제하게 만든다. 사람의 성실함에 기대면 2주 만에 무너진다.

```bash
#!/usr/bin/env bash
# bolt-check.sh - 볼트 종료 조건을 CI에서 강제한다
set -euo pipefail

export UOW=$(git rev-parse --abbrev-ref HEAD | grep -oE 'UOW-[0-9]{4}')
echo "대상 작업 단위: ${UOW}"

# 1) 승인된 명세에 존재하는 작업 단위인가
yq -e '.units[] | select(.id == env(UOW))' ai-dlc/inception/units-of-work.yaml > /dev/null

# 2) 미해결 질문이 남아 있으면 통합 불가
yq -e '.units[] | select(.id == env(UOW)) | .open_questions | length == 0' \
  ai-dlc/inception/units-of-work.yaml > /dev/null

# 3) 구현 코드에 출처 주석이 남아 있는가
grep -rq "UoW: ${UOW}" src/ || { echo '추적 주석 누락' >&2; exit 1; }

# 4) 수용 기준 테스트 통과
./gradlew test --tests '*OrderCancellation*'

echo '볼트 종료 조건 충족'
```

## 도입 전에 알아야 할 것들

**병목은 사라지지 않고 이동한다.** AI가 산출물을 쏟아내면 검토 대기열이 새 병목이 된다. 볼트를 짧게 유지하는 이유가 여기 있다. 한 번에 검토할 양을 사람이 감당할 수 있는 크기로 묶는 것이다.

**'사람이 검증한다'가 고무도장이 되는 순간 전부 무너진다.** 승인 버튼만 누르는 문화가 자리잡으면 AI-DLC는 검증 없는 자동 생성 파이프라인이 된다. 위 예제에서 수용 기준 테스트를 CI 게이트로 둔 것은 이 붕괴를 기계적으로 막기 위한 장치다.

**컨텍스트가 자산이다.** 의도, 결정, 제약이 채팅창에만 남아 있으면 다음 볼트에서 전부 다시 설명해야 한다. 저장소에 커밋하고 코드 리뷰 대상으로 삼아야 한다.

**아직 완성된 표준이 아니다.** AI-DLC는 2025년에 제안된 비교적 최근의 방법론이고, 대규모 조직의 장기 적용 사례는 축적되는 중이다. 규제 산업이나 감사 추적이 필요한 도메인이라면 승인 기록과 변경 이력을 어떻게 남길지 먼저 설계해야 한다. 전사 전환보다는 팀 하나, 서비스 하나에서 볼트 몇 번을 돌려보고 판단하는 편이 안전하다.

## 정리하면

AI-DLC의 핵심 주장은 '더 좋은 코딩 도구를 쓰자'가 아니다. **AI가 초안을 만드는 세계에서는 프로세스의 무게중심이 산출에서 의도와 검증으로 옮겨가야 한다**는 것이다. 스프린트 대신 볼트, 티켓 대신 작업 단위, 구두 합의 대신 버전 관리되는 컨텍스트로 바뀌는 이유가 전부 여기서 나온다.

다음 글에서는 기존 애자일·워터폴과 AI-DLC를 항목별로 비교하면서, 무엇이 실제로 달라지고 무엇이 이름만 바뀐 것인지 구분해 본다.
