## 왜 컨테이너가 아니라 Pod인가

앞 글에서 매니페스트 읽는 법을 다뤘으니 이번에는 가장 작은 배포 단위인 Pod를 살펴본다. 쿠버네티스는 컨테이너를 직접 스케줄링하지 않고, 항상 Pod로 한 번 감싸서 다룬다.

실제 애플리케이션은 혼자 돌아가는 경우가 드물다. 로그를 수집하는 에이전트, 설정을 주기적으로 받아오는 프로세스, mTLS를 처리하는 프록시처럼 **생명주기와 네트워크, 디스크를 함께 써야 하는 보조 프로세스**가 거의 항상 붙는다. 이것들을 이미지 하나에 모두 넣으면 supervisord 같은 프로세스 매니저가 필요해진다. 에이전트 버전 하나만 올리려 해도 앱 이미지 전체를 다시 빌드해야 한다. Pod는 이렇게 긴밀하게 묶이는 컨테이너들을 하나의 단위로 다루려고 만든 개념이다.

## 핵심 개념

- **네트워크 네임스페이스 공유**: Pod 안의 컨테이너들은 IP 하나를 함께 쓰고 `localhost`로 서로 통신한다. 그래서 같은 Pod 안에서 포트가 겹치면 안 된다.
- **볼륨 공유**: `emptyDir` 같은 볼륨을 여러 컨테이너가 마운트해서 파일로 데이터를 주고받는다.
- **pause 컨테이너**: 네트워크 네임스페이스를 유지하는 인프라용 컨테이너다. 노드에서 `crictl pods`를 실행하면 확인할 수 있다.
- **한 노드에서 함께 움직임**: Pod는 노드 하나에만 배치된다. 다른 노드로 옮겨질 때는 새 Pod로 다시 만들어지므로 IP도 바뀐다.

여기서 **사이드카 패턴**이 나온다. 메인 컨테이너의 코드는 건드리지 않고, 기능을 보태는 보조 컨테이너를 같은 Pod에 넣는 방식이다. 1.29에서 베타로 들어와 1.33에서 GA가 된 **네이티브 사이드카**는 `initContainers`에 `restartPolicy: Always`를 지정해서 만든다. 이렇게 하면 사이드카가 메인 컨테이너보다 먼저 시작되고, 메인 컨테이너가 끝난 뒤에 종료된다.

## 예시: 로그 수집 사이드카

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: web-with-logger
spec:
  initContainers:
  - name: log-shipper
    image: busybox:1.36
    restartPolicy: Always        # 네이티브 사이드카 지정
    command: ['sh', '-c', 'tail -F /var/log/app/access.log']
    volumeMounts:
    - name: logs
      mountPath: /var/log/app
  containers:
  - name: web
    image: nginx:1.27
    ports:
    - containerPort: 80
    volumeMounts:
    - name: logs
      mountPath: /var/log/nginx   # nginx 로그를 공유 볼륨에 기록
  volumes:
  - name: logs
    emptyDir: {}
```

```bash
kubectl apply -f web-with-logger.yaml
kubectl get pod web-with-logger -o wide

# 사이드카에서 localhost로 nginx 호출 (네트워크 공유 확인)
kubectl exec web-with-logger -c log-shipper -- wget -qO- localhost

# 사이드카가 읽어 들인 access 로그 확인
kubectl logs web-with-logger -c log-shipper -f
```

`wget`으로 요청을 보낸 직후 `log-shipper` 로그에 access 기록이 나오면 네트워크와 볼륨이 모두 공유되고 있는 것이다.

## 실무에서 주의할 점

1. **Pod를 직접 만들지 않는다.** 노드가 죽으면 Pod도 함께 사라지고 아무도 다시 띄워 주지 않는다. 운영 환경에서는 Deployment 같은 컨트롤러를 쓴다. 이 내용은 다음 단계에서 다룬다.
2. **리소스는 Pod 단위로 더해진다.** 스케줄러는 사이드카의 requests까지 합친 값으로 노드를 고른다. 사이드카에 limits를 빠뜨리면 노드 메모리를 조용히 잡아먹는 일이 생긴다.
3. **클러스터 버전을 확인한다.** 온프레미스 클러스터는 업그레이드가 늦는 경우가 많다. 1.28 이하에서 `containers`에 넣은 사이드카는 시작 순서가 보장되지 않는다. 또 Job의 메인 컨테이너가 끝나도 사이드카가 계속 돌아서 Job이 완료되지 않는 문제가 있다. 먼저 `kubectl version`으로 서버 버전을 확인하자.
4. **같은 Pod에 넣을지 판단하는 기준**은 독립적으로 스케일해야 하는지다. 앱과 DB를 한 Pod에 넣는 것은 대표적인 안티패턴이다.
5. **디버깅할 때는 `-c`를 붙이는 습관을 들인다.** 컨테이너가 여러 개인 Pod에서는 `logs`와 `exec`에 컨테이너를 지정해야 한다. 기동에 실패하면 `kubectl describe pod`의 Events부터 확인한다.
