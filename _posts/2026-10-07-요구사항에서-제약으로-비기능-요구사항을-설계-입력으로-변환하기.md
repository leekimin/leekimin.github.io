## 왜 필요한가

지난 글에서 품질 속성의 우선순위를 정했습니다. 그런데 "가용성이 1순위"라는 문장만으로는 설계를 할 수 없습니다. 이중화가 필요한지, 리전을 하나 더 둘지, 아니면 재기동 스크립트로 충분한지 판단할 근거가 없기 때문입니다.

현장에서 받는 요구사항은 대개 이런 식입니다.

- "장애 없이 돌아가야 합니다"
- "응답이 빨라야 합니다"
- "보안 심사를 통과해야 합니다"

이 문장들은 **설계 입력이 아니라 희망 사항**입니다. 아키텍트가 할 일은 이것을 **숫자와 조건이 붙은 제약(constraint)**으로 바꾸는 것입니다. 제약이 정해져야 "이 선택지는 탈락, 이 선택지는 과설계"라는 판단을 할 수 있습니다.

## 핵심 개념

### 1. 품질 속성 시나리오

모호한 요구를 6가지 요소로 쪼갭니다.

| 요소 | 의미 | 예 |
|---|---|---|
| 자극원 | 누가/무엇이 | 사용자 트래픽 |
| 자극 | 어떤 사건이 | 평소의 5배 유입 |
| 환경 | 어떤 상황에서 | 월말 정산 시간대 |
| 대상 | 어디에 | 주문 API |
| 응답 | 시스템이 어떻게 | 오토스케일로 처리 |
| 측정 | 무엇으로 판정 | p99 500ms 이하, 에러율 0.1% 미만 |

"측정" 칸을 채우지 못하면 아직 요구사항이 아닙니다.

### 2. 예산(Budget)으로 나누기

전체 목표를 구성 요소별로 배분해야 설계 입력이 됩니다. 대표적인 게 **가용성 예산**과 **지연 예산**입니다. 직렬로 연결된 컴포넌트의 가용성은 서로 곱해지므로, 각 컴포넌트가 99.9%여도 전체는 99.9%가 되지 않습니다.

### 3. 환경 제약은 요구사항보다 먼저 온다

폐쇄망이면 외부 SaaS 모니터링, 퍼블릭 컨테이너 레지스트리, 관리형 DB를 쓸 수 없습니다. 이 제약은 협상할 수 없는 **고정 제약**으로 따로 분류해 둡니다. 숫자로 정한 목표는 조정할 수 있지만 고정 제약은 그렇지 않습니다.

## 예시: 요구사항을 명세로 고정하기

저는 비기능 요구사항을 코드 저장소에 YAML로 두고 리뷰를 받습니다.

```yaml
# nfr/order-service.yaml
service: order-api
fixed_constraints:            # 협상 불가
  - network: air-gapped       # 폐쇄망, 외부 인터넷 불가
  - data_residency: on-prem   # 개인정보 외부 반출 금지
scenarios:
  - id: AVL-01
    stimulus: "단일 노드 장애"
    environment: "평시 운영"
    response: "트래픽 자동 우회"
    measure:
      availability_monthly: 99.9   # 월 43.2분 허용
      rto_seconds: 60
  - id: PERF-01
    stimulus: "평시 5배 트래픽"
    environment: "월말 정산"
    response: "수평 확장"
    measure:
      p99_latency_ms: 500
      error_rate_pct: 0.1
latency_budget_ms:            # p99 500ms 배분
  lb: 10
  app: 150
  db: 200
  external_auth: 100
  margin: 40
```

목표가 실현 가능한지는 간단한 계산으로 먼저 검증합니다.

```bash
# 월간 99.9%의 허용 다운타임
awk 'BEGIN{printf "허용 다운타임: %.1f분/월\n", (1-0.999)*30*24*60}'
# → 43.2분/월

# LB(99.95%) → App(99.9%) → DB(99.9%) 직렬 구성의 합성 가용성
awk 'BEGIN{a=0.9995*0.999*0.999; printf "합성 가용성: %.4f%%\n", a*100}'
# → 99.7502% : 목표 99.9% 미달
```

계산해 보면 "DB 단일 인스턴스로는 목표를 달성할 수 없다"는 결론이 나옵니다. 그러면 DB 이중화(Primary-Standby)가 **선택이 아니라 제약에서 도출된 결정**이 됩니다. 아키텍처 결정은 이렇게 근거를 갖춰야 합니다.

## 실무에서 주의할 점

1. **측정할 수 없는 숫자는 쓰지 않는다.** p99 지연을 목표로 잡았는데 수집 체계가 평균값만 제공한다면 그 목표는 검증할 수 없습니다. 목표를 정할 때 메트릭 수집 방법도 같이 정하세요.
2. **숨은 요구사항을 끌어낸다.** 백업 보존 기간, 감사 로그 보관 기간, 야간 배치 시간대 같은 항목은 아무도 말해 주지 않습니다. 운영팀과 보안팀을 반드시 인터뷰하세요.
3. **충돌을 드러낸다.** "RPO 0"과 "쓰기 지연 50ms 이하, 원거리 DR"은 물리적으로 함께 만족시키기 어렵습니다. 충돌을 숨기지 말고 우선순위표(지난 글)로 돌아가 결정하세요.
4. **비용을 함께 적는다.** 99.9%와 99.99%의 차이는 인프라 비용이 몇 배로 늘어나는 수준일 수 있습니다. 숫자마다 대략적인 비용을 붙여야 이해관계자가 현실적인 목표를 고릅니다.
5. **명세는 버전 관리한다.** 요구사항이 바뀌면 설계 근거도 바뀝니다. YAML과 결정 기록을 같은 저장소에 두면 "왜 이렇게 만들었는가"를 추적할 수 있습니다.

다음 단계에서는 이렇게 도출한 제약을 바탕으로 결정 자체를 기록하는 방법인 ADR(Architecture Decision Record)을 다룹니다.
