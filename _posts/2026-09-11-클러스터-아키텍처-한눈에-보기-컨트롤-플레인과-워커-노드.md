## 왜 구조를 먼저 봐야 하나

온프레미스에서 k8s를 직접 구축하면 매니지드 서비스가 감춰주던 것들이 전부 내 책임이 됩니다. etcd 백업도, API 서버 인증서 갱신도, 노드가 `NotReady`로 떨어졌을 때의 원인 추적도 마찬가지죠. "어느 컴포넌트가 무엇을 담당하는가"를 모르면 장애 때 로그를 어디서 봐야 할지조차 막막합니다.

## 큰 그림: 두 개의 평면

클러스터는 **컨트롤 플레인(두뇌)** 과 **워커 노드(일꾼)** 로 나뉩니다. 핵심은 *선언과 실행의 분리*입니다. 사용자는 "이런 상태였으면 좋겠다"를 선언하고, 컨트롤 플레인이 현재 상태와 비교해 차이를 좁히며, 워커 노드가 실제로 컨테이너를 띄웁니다.

### 컨트롤 플레인

| 컴포넌트 | 역할 |
|---|---|
| `kube-apiserver` | 모든 요청의 유일한 관문. 인증·인가·검증 후 etcd에 기록 |
| `etcd` | 클러스터의 유일한 진실. 모든 리소스 상태를 저장하는 KV 스토어 |
| `kube-scheduler` | 노드가 정해지지 않은 파드에 적합한 노드를 배정 |
| `kube-controller-manager` | 원하는 상태와 실제 상태의 차이를 메우는 루프 집합 |

### 워커 노드

- `kubelet` — API 서버로부터 자기 노드에 배정된 파드 명세를 받아 컨테이너 런타임에 실행을 지시하고, 상태를 보고
- `kube-proxy` — 서비스 가상 IP를 실제 파드 IP로 연결 (iptables/IPVS 규칙 관리)
- 컨테이너 런타임 — containerd, CRI-O 등 실제로 컨테이너를 실행하는 주체

## 직접 확인해보기

컨트롤 플레인 컴포넌트는 kubeadm 클러스터에서 static Pod로 떠 있습니다.

```bash
# 노드 구성 확인 (control-plane 롤 확인)
kubectl get nodes -o wide

# 컨트롤 플레인 컴포넌트 실체 확인
kubectl get pods -n kube-system -o wide

# static Pod 매니페스트는 디스크에 파일로 존재한다
ls /etc/kubernetes/manifests/
# etcd.yaml  kube-apiserver.yaml  kube-controller-manager.yaml  kube-scheduler.yaml
```

`kubectl apply` 한 줄이 흐르는 경로를 따라가 봅시다.

```bash
kubectl run demo --image=nginx

# 1) API 서버가 받아 etcd에 기록 → 이 시점엔 nodeName이 비어 있음
# 2) 스케줄러가 노드 배정 → 3) 해당 노드 kubelet이 실행
kubectl get events --sort-by=.lastTimestamp | tail -5
# Scheduled   Successfully assigned default/demo to worker-01
# Pulling     Pulling image "nginx"
# Started     Started container demo
```

이벤트의 `SOURCE` 컬럼을 보면 어느 컴포넌트가 무슨 일을 했는지 그대로 드러납니다.

```bash
kubectl get events -o custom-columns=SOURCE:.source.component,REASON:.reason,MSG:.message
```

## 실무에서 주의할 점

**etcd가 곧 클러스터입니다.** 정기 스냅샷 없이는 복구가 불가능합니다.

```bash
ETCDCTL_API=3 etcdctl snapshot save /backup/etcd-$(date +%F).db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key
```

- **컨트롤 플레인은 홀수 개(3대)** — etcd가 Raft 합의를 쓰므로 2대는 1대보다 나을 게 없습니다. 온프레미스 프로덕션이면 3대가 최소선입니다.
- **컨트롤 플레인이 죽어도 기존 파드는 계속 돕니다.** kubelet이 자율적으로 동작하기 때문입니다. 다만 새 배포·스케일링·자가치유는 멈춥니다. 장애 시 "서비스는 살아 있으니 침착하게" 대응할 근거가 됩니다.
- **인증서 만료는 조용히 찾아옵니다.** kubeadm 기본 유효기간은 1년입니다. `kubeadm certs check-expiration`을 모니터링에 넣어두세요.
