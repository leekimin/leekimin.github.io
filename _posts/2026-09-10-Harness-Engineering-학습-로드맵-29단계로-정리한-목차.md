## 왜 하네스인가

모델을 바꿔도 에이전트 품질이 기대만큼 오르지 않는 경험을 한 번쯤 해봤을 것이다. 실제로 성능을 좌우하는 것은 모델 주변을 감싸는 **하네스(harness)**, 즉 툴 정의, 컨텍스트 관리, 권한 모델, 루프 제어, 관측성의 총합이다. 이건 새로운 기술이라기보다 우리가 19년간 해온 서버 설계 문제의 변주에 가깝다. 다른 점은 호출자가 비결정적이고, 상태가 토큰이라는 희소 자원 위에 얹혀 있다는 것뿐이다.

이 시리즈의 목표는 "프롬프트를 잘 쓰는 사람"이 아니라 **에이전트 시스템을 설계하고 운영할 수 있는 사람**이 되는 것이다. 마치면 툴 스키마를 보고 문제를 예측하고, 컨텍스트 폭주와 무한 루프를 지표로 잡아내고, 회귀가 났을 때 어디를 먼저 볼지 판단할 수 있게 된다.

## 전체 목차

1. 하네스의 정의: 모델 호출과 에이전트 시스템의 경계
2. LLM 추론 루프 구조: 관찰, 판단, 행동의 반복
3. 컨텍스트 윈도우의 물리적 한계와 비용 구조
4. 시스템 프롬프트 설계 원칙과 계층 분리
5. 툴 정의 스키마: 이름, 설명, 파라미터 설계
6. 툴 결과 포맷팅: 모델이 읽기 좋은 출력 만들기
7. 에이전트 루프 구현: 종료 조건과 최대 반복 제한
8. 파일 시스템 접근 도구 설계와 경로 안전성
9. 셸 실행 도구 설계: 타임아웃, 스트리밍, 종료 코드
10. 검색 도구 설계: 정확도와 토큰 소비의 균형
11. 권한 모델 설계: 허용, 거부, 확인 요청의 삼분법
12. 샌드박싱과 격리: 프로세스, 파일, 네트워크 경계
13. 컨텍스트 압축 전략: 요약, 절삭, 외부 저장
14. 메모리 설계: 세션 내 상태와 세션 간 지속성
15. 서브에이전트와 위임: 컨텍스트 격리로 얻는 것
16. 병렬 실행과 동시성 제어: 충돌하는 도구 호출 다루기
17. 스킬과 플러그인: 하네스 기능의 확장 지점
18. 훅 시스템: 도구 호출 전후에 개입하기
19. MCP 연동: 외부 도구 서버를 붙이는 표준 경로
20. 관측성 설계: 트레이스, 토큰 회계, 턴 단위 로깅
21. 평가 체계 구축: 골든 태스크와 회귀 스위트
22. 비용과 지연 최적화: 프롬프트 캐싱과 모델 라우팅
23. 실패 모드 분류: 루프, 환각 호출, 조기 종료
24. 재시도와 복구: 멱등성과 부분 실패 처리
25. 프롬프트 인젝션 방어: 신뢰 경계와 데이터 취급
26. 장기 실행 작업 운영: 체크포인트와 재개
27. 멀티 유저 배포: 격리, 할당량, 감사 로그
28. 하네스 회귀 디버깅: 재현, 이분 탐색, 원인 격리
29. 운영 지표와 튜닝 루프: 무엇을 보고 무엇을 바꿀 것인가

## 왜 이 순서인가

1~7단계는 개념과 루프 구조를 잡는 구간이다. 여기를 대충 넘기면 이후의 모든 설계 판단이 감으로 흐른다. 8~19단계는 실제로 손을 움직이는 구현 구간으로, 툴과 권한과 컨텍스트라는 세 축을 하나씩 붙여 나간다. 20~29단계는 운영과 트러블슈팅이며, 관측성과 평가 없이는 나머지가 전부 추측이 되기 때문에 20~21단계를 운영 구간의 출발점에 두었다.

고비는 두 곳이다. 첫 번째는 13~16단계다. 컨텍스트 압축, 메모리, 서브에이전트, 동시성은 서로 얽혀 있어서 한 번에 이해되지 않는다. 두 번째는 23~25단계로, 여기서는 정답이 아니라 트레이드오프를 고르는 훈련이 필요하다. 막히면 멈추지 말고 다음 편으로 넘어간 뒤 돌아오는 편이 낫다.
