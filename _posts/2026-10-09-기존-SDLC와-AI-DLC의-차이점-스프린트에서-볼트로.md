## 왜 차이를 짚고 넘어가야 하나

지난 글에서는 AI-DLC가 무엇이고 왜 나왔는지 정리했습니다. 이번에는 기존 SDLC와 무엇이 다른지 봅니다. 이 차이를 "코딩 도구가 바뀌었다" 정도로 받아들이면, 2주짜리 스프린트에 Copilot만 끼워 넣고 끝나기 쉽습니다. 그러면 코드는 빨리 나와도 리뷰, 설계 합의, 배포 승인은 예전 속도 그대로라 병목이 그쪽으로 옮겨 갈 뿐입니다.

19년 동안 워터폴, 애자일, DevOps를 차례로 겪으면서 배운 게 하나 있습니다. 프로세스는 **가장 비싼 자원**을 기준으로 설계된다는 점입니다. SDLC에서는 그게 개발자의 구현 시간이었습니다. AI-DLC에서는 **사람의 판단과 검증 시간**이 가장 비쌉니다.

## 핵심 개념: 무엇이 바뀌는가

| 구분 | 기존 SDLC (애자일 기준) | AI-DLC |
|---|---|---|
| 주도권 | 사람이 계획하고 구현, AI는 보조 | AI가 계획을 제안하고 실행, 사람은 검증과 결정 |
| 반복 단위 | 스프린트 (1~4주) | 볼트(Bolt, 수 시간~수 일) |
| 요구사항 | 백로그, 유저 스토리 | 의도(Intent) → 유닛(Unit)으로 분해 |
| 협업 방식 | 개인 작업 + 비동기 리뷰 | Mob Elaboration / Mob Construction |
| 산출물 | 코드 중심, 문서는 뒤로 밀림 | 설계·결정 문서가 AI의 컨텍스트로 쓰이는 1급 산출물 |
| 단계 | 기획 → 설계 → 구현 → 테스트 → 배포 | Inception → Construction → Operations |

가장 큰 변화는 **대화의 방향**입니다. SDLC에서는 사람이 AI에게 "이 함수 만들어 줘"라고 지시했습니다. AI-DLC에서는 AI가 "이 요구사항을 이렇게 나눴고, 이런 점이 모호한데 어떻게 할까요?"라고 묻고, 사람이 답하고 승인합니다. 프로세스 안에 AI가 질문하고 사람이 결정하는 체크포인트가 들어가 있습니다.

## 예시: 볼트 단위 작업을 리포지토리에 남기기

AI-DLC에서는 AI가 만든 계획과 사람의 승인 기록이 다음 작업의 컨텍스트가 됩니다. 그래서 이 기록을 코드와 같은 리포지토리에서 버전 관리하는 편이 낫습니다. 아래는 제가 쓰는 구조의 예시입니다.

```bash
mkdir -p aidlc-docs/{inception,construction,operations}
touch aidlc-docs/state.md      # 현재 단계와 진행 상태
touch aidlc-docs/audit.md      # 사람의 승인과 결정 기록
git add aidlc-docs && git commit -m "chore: init AI-DLC workspace"
```

볼트 하나는 이렇게 정의합니다. 스프린트 계획서와 비교하면 기간이 짧고, 승인 게이트가 명시돼 있다는 점이 다릅니다.

```yaml
bolt:
  id: B-012
  unit: order-payment-retry
  duration: 6h
  intent: "결제 실패 시 멱등성을 보장하며 3회 재시도"
  ai_plan: aidlc-docs/construction/B-012-plan.md
  gates:
    - name: design-approval      # 도메인 모델과 API 설계 승인
      approver: backend-lead
    - name: test-review          # AI가 생성한 테스트 시나리오 검토
      approver: owner
  done_when:
    - "./gradlew test 통과"
    - "audit.md에 승인 기록 존재"
```

## 실무에서 주의할 점

1. **스프린트 이름만 볼트로 바꾸지 마세요.** 볼트가 짧은 이유는 사람의 검증을 자주, 작게 하기 위해서입니다. 승인 게이트 없이 기간만 줄이면 검증하지 않은 코드가 더 빨리 쌓일 뿐입니다.
2. **Mob 세션에는 결정권자가 반드시 있어야 합니다.** AI가 던지는 질문에 그 자리에서 답할 사람이 없으면 볼트가 멈춥니다. 인프라나 보안 관련 결정이라면 해당 담당자를 꼭 부르세요.
3. **문서는 AI의 장기 기억입니다.** 결정 기록을 남기지 않으면 다음 볼트에서 AI가 같은 질문을 반복하거나, 이미 기각한 설계를 다시 제안합니다.
4. **기존 CI/CD는 그대로 둡니다.** AI-DLC는 파이프라인을 대체하지 않습니다. AI가 만든 코드도 같은 테스트, 같은 정적 분석, 같은 배포 승인을 거쳐야 합니다.

다음 글에서는 AI-DLC의 첫 단계인 **Inception**에서 의도를 유닛으로 나누는 과정을 구체적으로 다루겠습니다.
